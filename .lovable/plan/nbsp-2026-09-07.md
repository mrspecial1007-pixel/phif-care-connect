P1 — Medication Identity & Prescription Foundation

OBJECTIVE

Build the foundational medication and prescription data model required to move PHIF Tracker from its current beneficiary-level dispensing model toward a future medication-level therapy model.

This phase is FOUNDATION ONLY.

P1 must create the data structures needed for:

Medication Identity

Commercial Products

Reusable Product ↔ Medication Mapping

Prescriptions

Prescription Items

It must not implement medication-level dispensing, medication eligibility, PHIF synchronization, claims, financials, or changes to the existing dispensing engine.

3. CORE DOMAIN MODEL

The target foundation is:

Beneficiary → Prescription → Prescription Items → Medication Identity

Separately:

Commercial Product → Product ↔ Medication Mapping → Medication Identity

The distinction is critical.

A medication represents the therapeutic identity.

A commercial product represents the physical/commercial product that may be purchased, stocked, supplied, or identified by barcode/brand/PHIF code.

A prescription item points to the therapeutic medication when known.

A prescription item may temporarily have no medication_id while the line is unmatched/draft.

---

4. MEDICATION IDENTITY

Create:

medications

This is a global shared reference catalogue.

It must not contain:

supplier

purchase price

selling price

reimbursement

pharmacy stock

package cost

patient information

pharmacy-specific operational data

Required fields

id UUID primary key

active_ingredient text NOT NULL

active_ingredient_normalized text NOT NULL

strength_value numeric NOT NULL

strength_unit text NOT NULL

strength_denominator_value numeric NULL

strength_denominator_unit text NULL

dosage_form text NOT NULL

dosage_form_normalized text NOT NULL

route text NULL

atc_code text NULL

notes text NULL

created_at

updated_at

---

5. MEDICATION IDENTITY RULE

The therapeutic identity is determined by:

normalized active ingredient + exact strength + dosage form

and, where applicable:

strength denominator + route

Do NOT use:

brand

manufacturer

supplier

barcode

package size

price

PHIF code

to define therapeutic identity.

Critical rule

Different strengths are always different medication identities.

Examples:

Metformin 500 mg ≠ Metformin 850 mg

Bisoprolol 5 mg ≠ Bisoprolol 10 mg

Never automatically merge them.

---

6. STRENGTH NORMALIZATION

Strength units must be canonicalized deterministically.

Examples:

mg

g

mcg

µg

mL

%

Do not allow visually different representations of the same canonical unit to create accidental duplicate medication identities.

For compound strengths such as:

5 mg / 5 mL

store:

strength_value = 5

strength_unit = mg

strength_denominator_value = 5

strength_denominator_unit = mL

Do not convert clinically meaningful strengths merely for convenience.

---

7. DOSAGE FORM NORMALIZATION

Store the original entered value:

dosage_form

and a deterministic canonical value:

dosage_form_normalized

The normalization must be deterministic and stable.

For example, common equivalent spellings may normalize to one canonical value where this is unambiguous.

Do not use unrestricted fuzzy matching to determine medication identity.

If normalization is ambiguous, retain the original value and require explicit mapping/review rather than guessing.

---

8. ACTIVE INGREDIENT NORMALIZATION

Store both:

original active_ingredient

deterministic active_ingredient_normalized

Normalization may include:

lowercase

whitespace normalization

deterministic Arabic letter normalization

diacritic removal

safe punctuation normalization

Do not perform fuzzy matching at read time.

Do not silently merge different active ingredients.

For combination products, do not force a single active ingredient.

---

9. MEDICATION UNIQUE IDENTITY

Create a database-level uniqueness rule preventing duplicate medication identities.

The identity must include:

active_ingredient_normalized

strength_value

strength_unit

normalized denominator value/unit where applicable

dosage_form_normalized

Include route in the identity only if the finalized clinical model determines that route materially distinguishes the medication identity.

Do not use COALESCE expressions inside a simple table constraint if PostgreSQL requires an expression index instead.

Use an appropriate unique index if necessary.

The uniqueness rule must be database-enforced.

---

10. COMMERCIAL PRODUCTS

Create:

commercial_products

This is a global catalogue/reference entity.

It represents a commercial product, not a therapeutic identity.

Fields

id UUID primary key

brand_name text NOT NULL

brand_name_normalized text NOT NULL

manufacturer text NULL

supplier text NULL

package_size numeric NULL

package_unit text NULL

barcode text NULL

phif_code text NULL

is_active boolean NOT NULL DEFAULT true

created_at

updated_at

---

11. COMMERCIAL PRODUCT RULES

Do NOT put medication_id directly on commercial_products.

The relationship must be represented by:

product_medication_mappings

This is intentional.

A commercial product may represent:

one medication

or, in the future, a combination product containing multiple medication identities.

Supplier, price, stock, package information and PHIF identifiers are commercial attributes.

They must never define therapeutic identity.

---

12. COMMERCIAL PRODUCT UNIQUENESS

Where a barcode exists:

Create a unique constraint/index on:

barcode

but only for non-null values.

For the commercial product deduplication key, use the appropriate normalized commercial fields, but treat it as a deduplication aid, not as therapeutic identity.

Do not prevent legitimate products from existing solely because their names are similar.

---

13. PRODUCT ↔ MEDICATION MAPPING

Create:

product_medication_mappings

This is the reusable bridge between commercial products and medication identities.

Fields

id UUID primary key

product_id UUID NOT NULL FK → commercial_products

medication_id UUID NOT NULL FK → medications

units_per_package numeric NULL

source text NOT NULL

confidence text NOT NULL

effective_from timestamptz NOT NULL DEFAULT now()

effective_to timestamptz NULL

created_by_pharmacy_id UUID NULL FK → pharmacies

created_at

updated_at

---

14. MAPPING SOURCE

Allowed values:

manual

phif

import

Do not allow arbitrary source values.

Use a CHECK constraint or equivalent database enforcement.

---

15. MAPPING CONFIDENCE

Allowed values:

confirmed

proposed

A proposed mapping must never silently become authoritative.

Only an explicitly confirmed mapping can be treated as an accepted mapping in future phases.

---

16. EFFECTIVE-DATED MAPPINGS

Mappings are historical records.

When a mapping is corrected:

1. close the current mapping with effective_to

2. create a new mapping with a new effective_from

3. never rewrite historical mapping meaning

4. never delete the historical mapping merely to replace it

This is necessary because future PHIF reconciliation may need to know which mapping was valid at a specific time.

---

17. COMBINATION PRODUCTS

A commercial product may map to multiple medications.

Example:

Product X contains:

Drug A 10 mg

Drug B 5 mg

It must be possible to have:

Product X → Medication A

and:

Product X → Medication B

both as confirmed mappings.

Therefore:

DO NOT create a unique active-confirmed constraint on product_id alone.

The uniqueness rule must instead prevent duplicate active mappings for the same:

product_id + medication_id

while allowing multiple medications for the same product.

This requirement is mandatory.

---

20. PRESCRIPTION STATUS

For P1 only:

draft

active

cancelled

Do NOT add completed.

A prescription cannot be considered completed until medication-level fulfillment exists in a later phase.

---

21. PRESCRIPTION VALIDITY

valid_until is nullable.

P1 stores this information only.

P1 must NOT use valid_until to calculate dispensing eligibility.

Eligibility belongs to later medication-level fulfillment logic.

---

22. PRESCRIPTION EXTERNAL REFERENCE

Create a partial unique constraint/index:

UNIQUE (pharmacy_id, external_ref)

where external_ref IS NOT NULL.

This prepares the model for future PHIF imports and idempotency.

Do not implement PHIF import now.

---

23. PRESCRIPTION INDEXES

At minimum:

(pharmacy_id, patient_id, prescription_date DESC)

Also create appropriate FK indexes where PostgreSQL does not automatically provide them.

25. PRESCRIPTION ITEM RULES

medication_id may be NULL.

This is intentional.

A prescription may initially contain a line such as:

> "دواء غير مطابق بعد"

The original prescription text must remain in:

raw_text

The system must not invent a medication identity.

A medication identity can be assigned later after explicit matching/review.

---

26. PRESCRIPTION ITEM UNIQUENESS

Create:

UNIQUE (prescription_id, line_number)

line_number must be stable within a prescription.

---

30. RLS / GRANTS

All five new tables must have RLS enabled.

Browser access must remain closed.

Do NOT grant:

anon

authenticated

direct access.

Use the established server-function architecture.

Server functions must require:

requirePharmacySession()

For pharmacy-private prescription operations:

pharmacy_id = [session.pharmacy](http://session.pharmacy)_id

must always be enforced server-side.

Never trust a client-supplied pharmacy ID.

---

31. PATIENT AUTHORIZATION

When creating or accessing a prescription:

The patient must be authorized through the existing pharmacy relationship model.

Use the established:

SERVED_BY

rule.

Do not create a new competing patient authorization mechanism.

A pharmacy must not be able to create/read a prescription for an unrelated patient simply by supplying a patient UUID.

---

32. SHARED PATIENTS

A patient may be served by both pharmacies.

This does NOT make prescriptions shared.

A prescription belongs to:

[prescriptions.pharmacy](http://prescriptions.pharmacy)_id

Therefore:

Pharmacy A sees A's prescriptions.

Pharmacy B sees B's prescriptions.

No pharmacy can browse the other pharmacy's prescription records.

The underlying patient identity remains globally shared according to the existing model.

---

33. GLOBAL REFERENCE DATA

Medication and commercial-product reference records may be shared between pharmacies.

However:

no patient data

no prescription data

no stock data

no prices

no supplier transaction history

no financial information

may be stored in these global reference tables.

---

34. CREATED_BY_PHARMACY_ID

product_medication_mappings.created_by_pharmacy_id is attribution metadata.

It must NOT make the mapping itself pharmacy-private.

The mapping remains a shared reference relationship.

If later requirements need pharmacy-specific mappings, that should be a future explicit design decision.

---

35. SEEDING

For P1:

Do not seed medication data automatically.

Start the catalogue empty.

Do not fabricate a PHIF medication catalogue.

Do not scrape or infer medication identities from existing dispensing transactions.

Do not convert historical beneficiary-level dispensing records into medication-level history.

If a verified PHIF medication catalogue becomes available later, it can be reviewed and imported through a dedicated seed/import phase.

---

36. HISTORICAL DATA

No historical backfill is allowed in P1.

Existing:

patients

dispensing transactions

due tracks

cycles

remain untouched.

Do not assign historical transactions to medications.

Do not create historical prescription records from existing dispensing data.

---

37. UPDATED_AT

All five tables must use the existing:

tg_touch_updated_at

mechanism consistently with the current database.

Do not create a competing timestamp trigger implementation.

---

38. DATABASE CONSTRAINTS

Where practical, enforce domain rules in PostgreSQL rather than relying only on TypeScript.

At minimum enforce:

required fields

valid enum-like source values

valid prescription statuses

valid mapping source

valid mapping confidence

medication identity uniqueness

product barcode uniqueness where non-null

prescription external reference uniqueness where non-null

prescription line uniqueness

valid foreign keys

---

39. DELETE BEHAVIOR

Be conservative with deletion.

Medication identities and commercial products should not be casually deleted once referenced.

Prefer deactivation/history over destructive deletion.

Prescription items should cascade with their parent prescription only as explicitly defined.

Do not add destructive cascade relationships that could erase reference history unexpectedly.

---

40. SERVER FUNCTIONS

P1 should introduce only the minimum server infrastructure required for the new foundation.

If server functions are needed, they must follow the P0 architecture:

require pharmacy session

authorize the patient through SERVED_BY

enforce pharmacy ownership

never trust client pharmacy IDs

return not-found for unauthorized pharmacy-private records where appropriate

Do not build a large CRUD API or UI in P1 unless required for validating the foundation.

46. ACCEPTANCE CRITERIA

P1 is accepted only when:

1. The five tables exist exactly according to the approved model.

2. Medication identity is structurally distinct from commercial product identity.

3. Different strengths never automatically match.

4. Combination products are supported.

5. Mapping history is preserved.

6. Prescription ownership is pharmacy-private.

7. Prescription items can remain unmatched.

8. No historical medication data has been fabricated.

9. No existing production table has been modified.

10. Existing dispensing behavior is unchanged.

11. RLS and grants follow the P0 security model.

12. Cross-pharmacy prescription isolation is verified.

13. Build and typecheck pass.

14. Regression tests pass.

15. Rollback migration is prepared.

16. No P2 functionality has been implemented.
